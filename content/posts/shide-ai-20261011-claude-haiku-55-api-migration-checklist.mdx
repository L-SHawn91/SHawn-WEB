 새   모델   ID로   배포를   끝냈는데   일부   요청이  400  오류를   내거나,   인터페이스에는   답변이   없는   것처럼   보이거나,   예상보다   빨리   토큰   한도에   닿는다면   모델   이름만   바꾼   전환으로는   충분하지   않을   수   있습니다.  Haiku  4.5에서  Haiku  5.5로   옮길   때는   토크나이저,  thinking  설정,   응답   블록을   읽는   방식,   도구   호출   루프,   저장해   둔   대화   이력을   함께   확인해야   합니다.

 Anthropic이  [2026년 10월 7일 출시한 Claude Haiku 5.5](https://www.anthropic.com/claude-haiku-5-5) 는   고빈도·저지연   작업을   겨냥한   모델입니다.   이   글은  Haiku  4.5를   사용하는  Messages API  클라이언트가   새   모델로   옮길   때   확인할   지점을   다룹니다.

 Anthropic의   공식  migration  guide는  Messages  API에서  Haiku  4.5를  Haiku  5.5로   바꿀   때   생기는   구체적인   호환성   차이를   열   가지   항목으로   정리합니다.   모든   앱이   열   가지를   전부   수정해야   하는   것은   아닙니다.   어떤   요청   구조와   기능을   실제로   쓰는지에   따라   필요한   변경이   달라집니다.

 이   글은   출시일이나   성능표를   다시   비교하기보다,   운영   중인  API  호출에서   무엇이   실제로   달라지는지   설명합니다.   핵심은   전체   서비스를   한   번에   옮기는   것이   아니라,   기존   요청과   저장된   대화가   어디에서   달라질   수   있는지   작은   검증   묶음으로   확인하는   것입니다.

## 모델 ID 교체가 간단한 경우와 그렇지 않은 경우는 다릅니다

Claude Haiku  5.5는  [2026년 10월 7일 출시됐으며](https://platform.claude.com/docs/en/models/haiku-5-5/overview), Claude  API에서   사용하는   모델   ID는  `claude-haiku-5-5` 입니다.   이전  Haiku 4.5  요청에서  `claude-haiku-4-5-20251001`  또는  `claude-haiku-4-5` 를   지정했다면,   새  API  모델   ID로   바꾸는   것이   전환의   시작입니다.  Haiku 5.5  ID에는   날짜   접미사가   없고   별도   alias도   없습니다.

 다만   이   ID를   모든   호스팅   환경에   그대로   복사하면   안   됩니다.  [Anthropic의 migration guide](https://platform.claude.com/docs/en/models/haiku-5-5/migration-guide) 는  Amazon Bedrock, Google Cloud, Microsoft Foundry, Claude Platform on  AWS에   서로   다른   모델  ID  형식을   제시합니다.   SDK나   배포   플랫폼이  Anthropic  API를   직접   부르는지,   중간   제공자를   거치는지   먼저   확인해야   합니다.   이   차이를   놓치면   모델은   열렸는데   요청은   잘못된   ID로   보내는   일이   생깁니다.

Anthropic Managed  Agents를   사용하는   경우에는   공식   안내상   모델   이름을   바꾸는   것   외의   변경이   필요하지   않습니다.   이   예외는   Anthropic이   관리하는   해당   실행   환경에   대한   설명입니다.   자체  Messages API  클라이언트나   다른   서비스   래퍼에도   같은   단순성이   보장된다는   뜻은   아닙니다.

 Anthropic은  [Haiku 5.5를 분류·추출·라우팅처럼 규모가 크고 지연시간에 민감한 작업](https://www.anthropic.com/claude-haiku-5-5) 에   맞춘   모델로   소개합니다.   이   설명은   제품의   용도에   대한   안내이지,   특정   서비스에서   더   빠르거나   비용이   낮다는   독립   측정   결과는   아닙니다.   실제   선택은   현재   시스템의   응답시간,   정확도,   거절률,   토큰   사용량으로   확인해야   합니다.

## 같은 문장을 다시 세어야 토큰 한도가 보입니다

Haiku  5.5는   이전  Haiku  4.5와   다른   최신   토크나이저를   사용합니다.   Anthropic의  [모델 문서](https://platform.claude.com/docs/en/models/haiku-5-5/overview) 는   같은   입력   텍스트가   평균적으로   약  30%  더   많은   토큰으로   계산될   수   있다고   설명하면서,   증가   폭은   내용에   따라   달라진다고   덧붙입니다.   따라서   이전   버전에서   저장해   둔  prompt token  count를   새   모델의   비용이나   한도   계산에   재사용하면   안   됩니다.

 예를   들어   기존   평가   프롬프트가  Haiku  4.5에서   약   10,000토큰이었다면,  30%  증가를   단순   적용한   값은   약   13,000토큰입니다.   이   수치는   설명을   위한   계산일   뿐,   실제   프롬프트의   토큰   수를   예측하는   보장은   아닙니다.   공식   문서도   새   모델   ID를   지정해   프롬프트를   다시   세도록   안내합니다.   입력에   코드,   여러   언어,  JSON,  긴   문서가   들어간다면   직접   다시   측정해야   합니다.

 Anthropic은  Messages API  요청·응답과  streaming  event의   형태   자체는   그대로라고   안내합니다.   달라지는   것은   토큰으로   측정하는   예산과   응답   안의  content block  처리입니다.   토큰   수가   늘면   컨텍스트   창에서   같은   입력이   차지하는   비중이   달라지고,   이전   버전에   맞춰   둔  `max_tokens` 가   출력   끝을   잘라낼   수도   있습니다.  Haiku  5.5는  adaptive  thinking을   기본으로   사용하며  thinking  토큰도  `max_tokens`  안에   포함됩니다.   그래서   이전   응답   길이를   그대로   기대하기보다,   실제   응답에서   최종   텍스트가   남는지와  `stop_reason` 이   어떻게   끝나는지를   함께   확인해야   합니다.

 가격표만   보고   비용을   계산하는   일도   피해야   합니다.  [현재 모델 요금](https://platform.claude.com/docs/en/models/haiku-5-5/overview) 은   프롬프트가   100,000토큰   이하일   때   입력   100만   토큰당  $0.10,  출력   100만   토큰당   $0.50이며,   100,000토큰을   넘으면   각각   $0.50과   $2.50입니다.   이   낮은   구간에서   입력   10,000토큰만   계산하면   $0.001이고,   앞의   예시처럼   입력이   13,000토큰이면   $0.0013입니다.   두   값   모두   출력   토큰,   캐시   읽기·쓰기,   배치   요금을   제외한   입력비   예시입니다.   재토큰화로   요청이   경계에   가까워질   수   있고,   thinking과   출력   길이도   청구액에   영향을   줍니다.   Anthropic이   소개한   평균   비용   절감치를   각자의   서비스   비용으로   그대로   적용하지   말고,   새   모델의   실제  `usage` 를   사용해   다시   계산하는   편이   안전합니다.

## Thinking 설정을 바꾸면 응답을 읽는 코드도 달라집니다

Haiku  4.5에서  `thinking: &#123;"type": "enabled", "budget_tokens": N&#125;` 으로   고정   예산을   보내던   요청은  Haiku  5.5에서  400  오류를   반환합니다.  Haiku  5.5에서는  `thinking: &#123;"type": "adaptive"&#125;` 를   사용하고,  `output_config.effort` 로   작업의   깊이를   조절하는   방식이   안내됩니다.  `low`, `medium`, `high`  같은  effort  선택은   이전  `budget_tokens` 와   같은   숫자   예산을   그대로   옮기는   동작이   아닙니다.

 더   놓치기   쉬운   변화는   thinking을   요청에   직접   지정하지   않아도   응답에  thinking  block이   먼저   들어올   수   있다는   점입니다.   기존   코드가  `content[0]` 을   최종   답변으로   간주했다면,   그   자리에   생각   블록이   와서   화면에는   답이   없는   것처럼   보일   수   있습니다.   응답   배열의   위치가   아니라   각   블록의  `type` 을   확인하고,   사용자에게   표시할   텍스트   블록을   골라야   합니다.

 도구   결과와   함께  thinking  block을   다시   보낼   때에는   받은   블록을   임의로   요약하거나   재구성하지   말고   원형   그대로   전달해야   합니다.   작은  `max_tokens` 를   그대로   유지하면   모델이   thinking에   한도를   사용한   뒤   텍스트를   내기   전에   끝날   수도   있습니다.   따라서   응답   파서,   tool-result를   붙이는   코드,   빈   텍스트   처리와   최대   출력   설정을   하나의   통합   테스트로   확인해야   합니다.

## 샘플링 값과 assistant prefill은 요청에서 걷어내야 합니다

Haiku  4.5에서   조정하던  `temperature`, `top_p`, `top_k` 도   다시   살펴봐야   합니다.  Haiku  5.5의  migration  guide는   세   값을   요청에서   빼고   프롬프트로   동작을   유도하도록   안내합니다.   허용되지   않는   값이나   조합은  400  오류를   돌려줄   수   있습니다.   라이브러리   기본값이   자동으로   필드에   들어가는지까지   확인하지   않으면   코드에서   지웠다고   생각한   설정이   실제   payload에   남을   수   있습니다.

`messages`  끝에  assistant  역할의   미완성   문장을   두고   모델이   이어   쓰게   하던   방식도  Haiku  5.5에서는   거절됩니다.   출력   형식을   맞추려는   목적이라면   구조화된   출력   기능이나   enum이   있는  tool  schema를   검토할   수   있고,   특정한   시작   문장을   원했다면  system  prompt에   요구를   적을   수   있습니다.   중단된   응답을   이어   붙이는   용도라면   앞선   텍스트를  user  turn에   포함하는   방식이   안내됩니다.

 이   변경은   프롬프트   몇   줄만   고치는   작업이   아닐   수   있습니다.   서버에서   메시지를   직렬화하는   공통   함수,   재시도   코드,   SDK가   기본으로   넣는   파라미터까지   추적해야   합니다.   한   요청만   고친   뒤   전체   시스템이   호환된다고   결론   내리기보다,   서비스에서   사용하는   요청   유형별로   payload를   기록해   비교하는   편이   낫습니다.

## 컴퓨터 도구를 쓴다면 선언과 실행 루프를 함께 바꿔야 합니다

 텍스트   요청만   보내는   서비스라면   이   부분을   건너뛸   수   있습니다.   하지만  Claude API  또는  Google  Cloud에서  computer  use를   쓰고   있다면  Haiku  4.5의  `computer_20250124`  도구   선언을   그대로   유지할   수   없습니다.  Haiku  5.5는  `computer_toolset_20260801` 을   사용하며,   예전   도구   선언을   보내면  400  오류가   발생합니다.

 도구   이름을   한   군데   바꾸는   것만으로도   부족합니다.   Anthropic은   도구   호출을   처리할   때  `input.action` 만   보지   말고   각  `tool_use`  block의  `name` 과  `toolset_name` 을   기준으로   분기하고,   한   응답의   모든   도구   요청을   처리한   뒤   결과에  `toolset_name` 을   되돌려   주도록   안내합니다.   확대   기능이   기본   활성화됐으나   실행   환경이   지원하지   않는다면   도구   구성에서   끌   수   있습니다.  `computer-use-2025-01-24` 와  `fine-grained-tool-streaming-2025-05-14` beta  header가   남아   있으면  toolset  요청이  400  오류를   낼   수   있으므로,   실제   payload에서   두   값을   확인해야   합니다.

Haiku  5.5는  Claude  API와  Google  Cloud에서   웹페이지   안의   작업을   위한  browser-use  tool도   지원합니다.   이   기능을   새로   도입하는   일과   기존  computer-use  호출을   이전하는   일은   별도   변경입니다.   도구를   쓰지   않는   기존   서비스를   대상으로   새   브라우저   기능까지   한   번에   켜면,   모델   전환의   영향과   기능   추가의   영향을   구분하기   어려워집니다.

## 저장된 대화는 account와 앞선 메시지에 묶일 수 있습니다

 여러   사용자의   대화를   데이터베이스에   저장했다가   다시   모델로   보내는   서비스는  thinking  block을   어떤   account에서   만들었는지   기록해야   합니다.  Haiku  5.5의  thinking  block은   이를   만든  account  또는   연결된   account에서만   읽을   수   있습니다.   다른   account에서   block을   다시   보내면   요청   자체는   성공하더라도   해당   block은   모델에   전달되기   전에   빠질   수   있습니다.   에러가   없다는   사실만으로   과거   reasoning까지   복원됐다고   판단하면   안   됩니다.

 앞선   대화   내용이   바뀌었는지도   중요합니다.  thinking block  앞에   있던  `system`, `tools`,  이전  `messages` 의   내용이   달라지면   새   account에서는  400  오류가   날   수   있습니다.  prefix  확인은   2026년   8월   31일  00:00 UTC  이후   만든   account에   기본   적용되며,   그보다   오래된   account는  `thinking.block_binding.prefix_mismatch_behavior` 를   설정한   요청에서   확인됩니다.  [Anthropic의 preserved-thinking 문서](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking) 는  mismatch  설정에   따라   block을   거부하거나   제거할   수   있다고   설명합니다.  account  연령에   따라   동작이   갈리지   않도록   대화   앞부분을   바꾸지   않고   뒤에만   이어   붙이는   편이   안전합니다.

 실무적으로는   저장된   대화를   템플릿으로   다시   조립하는   코드,   오래된  tool  result를   삭제하는   요약   로직,   시스템   지침을   매   요청마다   다시   쓰는   미들웨어가   영향을   받을   수   있습니다.   각   turn의   원본   payload와  account  식별자를   보존하고,   다른   account에서   재생할   때   어떤   block이   유지되는지   별도   테스트해야   합니다.   단순한  200  응답만으로   대화   맥락이   완전히   재생됐다고   볼   수는   없습니다.

## 거절 응답과 우선 처리 용량은 별도 경로로 점검해야 합니다

Haiku  5.5는   안전   분류기가   요청을   거절할   수   있으며,  API  응답은  `stop_reason: "refusal"` 과   거절   범주를   반환할   수   있습니다.  Haiku  4.5에서   같은   요청이   통과했더라도   새   버전에서   같은   동작을   보장하지는   않습니다.   Anthropic의  [Haiku 5.5 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5) 는  server-side  fallback이   없다고   명시합니다.   클라이언트는   거절   상태를   정상적인   응답   분기로   처리해야   하며,   같은   요청을   반복   전송하면   해결될   것이라고   가정하면   안   됩니다.

 여기서   필요한   것은   안전장치를   우회하는   재시도   규칙이   아닙니다.   거절   응답이   왔을   때   사용자에게   어떻게   알릴지,   작업을   안전하게   종료할지,   별도의   승인된   대체   경로가   있는지   제품   정책을   확인하는   일입니다.   거절   범주를   로그로   남길   때는   필요한   운영   정보만   보관하고   민감한   입력을   불필요하게   저장하지   않는지도   검토해야   합니다.

 또한   조직이  Haiku  4.5의  Priority Tier  용량을   사용했다면  Haiku  5.5가   같은   우선   처리   조건을   지원한다고   추정하면   안   됩니다.   Anthropic은  Haiku  5.5에서  Priority  Tier를   지원하지   않는다고   안내합니다.   요청   처리량이   중요한   서비스는   모델  ID  변경과   별도로   계정별   용량·처리   지연·서비스   등급을   확인해야   합니다.

## 전체 전환보다 작은 검증 묶음부터 비교하는 편이 낫습니다

 첫   비교는   실제   사용자   요청이   아닌   고정된   평가   묶음으로   시작할   수   있습니다.   평소   쓰는   짧은   질문,   긴   문맥,  JSON  형식,  tool call,  이전   응답을   이어   가는   대화,   거절될   수   있는   요청을   나눠   같은   입력을   두   모델에   보냅니다.  Haiku  5.5에서는   새   모델   ID로   토큰을   다시   세고,  `content`  배열의   모든   block을   확인하며,  tool-use  요청이   한   응답에   여러   개   들어오는   경우도   포함해야   합니다.

 비교   결과는   정확도   하나로   끝나지   않습니다.   각   요청이  400  오류를   내는지,   출력이  `max_tokens` 에서   잘리는지,   refusal이   정상적인   상태로   처리되는지,   토큰   사용량과   실제   지연시간이   어떻게   달라지는지   살펴봐야   합니다.   긴   prompt라면   100,000토큰   가격   경계에   가까운   사례를   별도로   넣고,   저장   대화를   재생한다면   같은   account에서의   재생과   account를   바꾼   재생을   구분해야   합니다.

 그   다음에는   일정   비율의  canary  요청으로   실제   서비스의   변화를   확인합니다.   오류나   출력   품질이   허용   범위를   벗어날   때   즉시  Haiku  4.5로   되돌릴   수   있도록   모델   선택   설정을   분리해   두는   것이   좋습니다.   Anthropic의  migration  guide가   모델별   수정   항목을   제시하더라도,   서비스의   수용   기준과   롤백   조건은   각   운영팀이   정해야   합니다.   문서에   있는   호환성   안내는   테스트를   대신하지   않습니다.

## 무엇을 바꾸고 무엇을 측정할지 함께 정해야 합니다

Haiku  5.5로   옮길   때   모든   서비스가   같은   양의   수정을   해야   하는   것은   아닙니다.   단순한  Messages API  호출은   모델   ID와   토큰   사용량을   확인하는   데서   끝날   수도   있지만,  thinking  block을   저장하거나  assistant prefill·computer  use를   활용한다면   요청   규격과   응답   처리까지   달라집니다.   대화   재생과   거절   응답은   정상  HTTP  응답만으로   놓치기   쉬운   변화입니다.

 따라서   지금   할   일은   모든   호출을   한꺼번에   바꾸는   것이   아니라,   실제로   사용하는   기능을   확인하고   각각의   요청을   새   모델에서   다시   측정하는   것입니다.   공식   문서는   전환   지점을   알려주지만,   실제   비용·오류율·정확도는   각   서비스의   평가   묶음에서   확인해야   합니다.
