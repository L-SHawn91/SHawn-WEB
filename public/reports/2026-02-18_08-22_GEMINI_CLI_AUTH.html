Executive Summary

  • 원인: Gemini CLI의 Login with Google 인증 경로가 정책 플래그/계정 상태 영향으로 차단되었습니다.
  • 영향: 동일 계정에서도 인증 경로에 따라 성공/실패가 갈리며, 로그인 경로는 실패하고 API Key 경로는 정상 응답합니다.
  • 운영 결론: Gemini 운영을 중단할 필요는 없으며, API Key 경로를 표준 경로로 고정하고 Login 경로는 진단용으로 분리해야 합니다.
  • Cause: Gemini CLI Login with Google path is blocked by policy/account-state conditions.
  • Impact: Success depends on auth path: login fails while API-key calls remain healthy.
  • Ops decision: Keep Gemini active via API-key as the default path, and isolate Login path as diagnostic-only.

운영 액션 플랜

Operational Action Plan

  • 표준 호출 경로를 Gemini API Key로 고정하고, Login 경로는 진단/복구 테스트 용도로만 사용
  • 실패 코드 정책: 401/403 즉시 격리, 429 30~60분 쿨다운, timeout 1회 재시도
  • 환경 분리: 로컬 개발(Login 가능 시)과 운영 서버(API Key 전용)를 분리해 재현성과 안정성 확보
  • 정기 점검 리포트에 경로별 상태(Login/API)와 최근 24시간 오류율을 함께 기록
  • Set Gemini API key path as the production default; keep Login path for diagnostics only.
  • Error policy: isolate on 401/403, cooldown 30–60m on 429, retry once on timeout.
  • Separate environments: local development vs production API-key path for reproducibility.
  • Track path-level health (Login/API) and 24h error rates in regular ops reporting.

Deep Dive: Why outcomes differ by auth path

이번 사례는 “Gemini가 전체적으로 죽었다”가 아니라, 인증 계층이 분리되어 작동한다는 점을 보여줍니다. 즉, 동일한 모델/계정이라도 인증 토큰 발급 체인, 정책 판정 지점, 지역/세션 상태에 따라 실제 호출 가능 여부가 달라질 수 있습니다. 운영에서는 이 차이를 구조적으로 반영해야 장애 전파를 막을 수 있습니다.

특히 로그인 기반 흐름은 사용자 세션 상태, 계정 정책 플래그, 브라우저/OAuth 토큰 조건에 영향을 받는 반면, API Key 기반 흐름은 서버 측 자격증명 검증으로 단순화됩니다. 그래서 실무에서는 API Key 경로를 기준선으로 삼고, 로그인 경로는 부가 채널로 관리하는 방식이 재현성·안정성 측면에서 유리합니다.

This incident indicates path-level divergence rather than a full Gemini outage. The same account/model may produce different outcomes depending on token issuance chain, policy checkpoints, and session state. In production operations, this must be modeled explicitly to avoid cascading failures.

운영 체크리스트 (Gemini 전용)

Operational checklist (Gemini-only)

  • 경로 표준화: 배치/자동화/서버 호출은 API Key로만 실행
  • 진단 분리: Login 경로는 주기 진단 1회/일로 제한, 운영 경로와 분리
  • 모니터링: 401/403/429/timeout 비율을 시간대별로 기록
  • 복구 절차: 429 급증 시 쿨다운 후 재시도, 401/403은 즉시 자격증명 재검증
  • 리포트 표준: 결론 1줄 + 원인 2줄 + 조치 2줄 포맷 고정
  • Standardize path: use API key for all production/server automation.
  • Isolate diagnostics: run Login-path checks separately from production calls.
  • Monitor: track 401/403/429/timeout rates by time window.
  • Recovery: cooldown on 429, immediate credential validation on 401/403.
  • Reporting: fixed format—1-line conclusion, 2-line cause, 2-line action.

FAQ (검색 확장 블록)

FAQ (SEO Expansion Block)

Q. Google 로그인만 막히면 Gemini를 완전히 중단해야 하나요?
A. 아닙니다. API Key 경로가 정상이라면 경로를 분리해 제한 운영하는 것이 실무적으로 효율적입니다.

Q. 429가 반복될 때 가장 안전한 운영 방식은?
A. 해당 경로만 30~60분 쿨다운하고, Kimi/OpenCode 보조 경로로 트래픽을 분산하는 것이 안정적입니다.

Q. Should Gemini be fully disabled if only Google Login fails?
A. No. If API-key path is healthy, keep Gemini in restricted path-specific operation.

Q. What is the safest strategy under repeated 429?
A. Cool down the affected route for 30–60 minutes and shift load to Kimi/OpenCode fallback tracks.
