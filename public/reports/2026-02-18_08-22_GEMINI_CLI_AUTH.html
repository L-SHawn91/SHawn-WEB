Gemini CLI 로그인 차단 이슈, 왜 ‘전체 장애’처럼 보였을까

이번 이슈의 핵심은 모델 자체 장애가 아니라 인증 경로 분리였습니다. 로그인 경로가 막혀도 API Key 경로가 살아 있으면 운영은 계속할 수 있습니다.

2026-02-18 08:22 KST · SHawn Ops Blog

처음 보는 사람을 위한 30초 요약

  • 증상: Gemini CLI의 Login with Google 방식이 실패
  • 반대 증거: 같은 시점에 API Key 방식은 정상 응답
  • 결론: 모델 품질 문제가 아니라 인증 경로 분리 이슈
즉, “Gemini 전체 장애”가 아니라 “Gemini에 들어가는 문 중 하나가 막힌 상태”였습니다.

왜 이 이슈가 실무에서 크게 보였나

운영팀 입장에서는 같은 모델 호출인데 어떤 환경에서는 되고, 어떤 환경에서는 안 되면 원인 분리가 늦어집니다. 특히 로그인 기반 호출과 API Key 기반 호출이 혼합돼 있으면 장애가 더 크게 보입니다.

이번 케이스도 마찬가지였습니다. 처음에는 모델 장애처럼 보였지만, 호출 경로를 나눠서 확인하니 이슈가 빠르게 분리됐습니다.

오류코드별 플레이북 (Gemini-only)

  • 401/403: 자격증명/권한 검증 후 해당 경로 즉시 격리
  • 429: 30~60분 쿨다운 후 재시도 (연타 금지)
  • timeout: 1회 재시도 후 다음 주기로 이관
# 운영 공통 원칙

- Login 경로: 일 1회 진단용
- 보고 형식: 결론 1줄 + 원인 2줄 + 조치 2줄

시각화 2) 전/후 운영 효과

FAQ

Q. Login이 막히면 Gemini를 중단해야 하나요?
A. 아닙니다. API Key 경로가 정상이라면 운영은 지속 가능합니다.

Q. 왜 모델 변경보다 경로 분리가 우선인가요?
A. 이번 이슈는 모델 품질 문제가 아니라 인증 경로 안정성 문제이기 때문입니다.

Q. 가장 먼저 바꿀 1가지는 무엇인가요?
A. 배치/크론/서버 호출 경로를 API Key로 고정하는 것입니다.
