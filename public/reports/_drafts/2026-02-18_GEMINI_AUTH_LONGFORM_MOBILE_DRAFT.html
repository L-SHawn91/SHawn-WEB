Gemini CLI 인증 장애, 왜 ‘전체 장애’가 아니었나

이번 이슈의 핵심은 모델 자체 장애가 아니라 인증 경로 분리입니다. 운영 표준을 Login 중심에서 API Key 중심으로 재정의하면 장애 전파를 막을 수 있습니다.

2026-02-18 · SHawn Ops Blog · 검수 전 초안

1) 처음 보는 사람을 위한 30초 요약

  • 무슨 일? Gemini CLI에서 Login with Google 경로가 차단됨
  • 근데 왜 계속 쓸 수 있지? API Key 경로는 정상이라 호출 가능
  • 그래서 뭘 해야 함? 운영 기본 경로를 API Key로 고정하고 Login은 진단용 분리

2) 시각화: 인증 경로별 상태

해석: “Gemini 전체 장애”가 아니므로 모델 교체보다 경로 분리 운영이 우선입니다.

3) 왜 이런 현상이 발생하나

같은 Gemini 호출이라도 인증 체인이 다르면 실패 지점도 달라집니다. Login 기반 경로는 세션/OAuth/정책 플래그 영향을 크게 받고, API Key 경로는 서버 자격증명 검증으로 단순화되어 재현성이 높습니다.

운영에서 중요한 건 “어떤 모델이 최고인가”보다 “어떤 경로가 일관되게 살아있는가”입니다. 이번 이슈는 그 차이를 명확하게 보여준 사례입니다.

4) 실무 조치안 (Gemini-only)

  • 운영 자동화/배치는 Gemini API Key 경로로만 고정
  • Login 경로는 하루 1회 헬스체크로 분리
  • 401/403 즉시 격리 + 자격증명 검증
  • 429 발생 시 30~60분 쿨다운 후 재시도
  • timeout은 1회 재시도 후 다음 주기로 이관

7) FAQ

Login이 막히면 Gemini를 중단해야 하나요?
아닙니다. API Key 경로가 정상이라면 운영 지속이 가능합니다.

왜 모델 교체보다 경로 분리가 우선인가요?
이번 유형은 모델 품질 이슈가 아니라 인증 경로 안정성 이슈이기 때문입니다.
